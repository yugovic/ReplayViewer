# 画像支援コース生成 設計書

- **状態**: Draft
- **対象**: `track-creator` Track Editor
- **作成日**: 2026-07-10
- **方針**: 自動生成結果を確定値にせず、人間が画像と信頼度を確認して適用・修正する

## 1. 背景

現在の Track Editor は、中心線を基準に左右の舗装端を編集し、縁石区間を追加して GLB を生成できる。航空写真と走行ラインも重ねられるが、幅と縁石の入力は手作業である。

本機能では、地理参照済み航空写真またはユーザー画像から次の候補を生成し、既存 Editor の編集フローへ渡す。

- **左右舗装端**: 中心線から左右端までの距離列
- **縁石**: 中心線弧長上の開始・終了・左右・推定幅
- **将来対象**: 画像だけからの中心線候補

完全自動化は目標にしない。画像の影、樹木、ランオフ、ピットロード、解像度不足による誤認識を前提に、候補の可視化、信頼度、人間による承認、Undo を必須とする。

## 2. 目的

- **作業短縮**: 全周を手作業でトレースする時間を減らす
- **左右独立幅**: 非対称な舗装端を `road.edges.left/right` として生成する
- **安全な適用**: 解析中およびプレビュー中は `TrackDef` を変更しない
- **監修支援**: 低信頼区間を明示し、人間が重点確認できるようにする
- **再現性**: 入力、設定値、解析バージョン、結果を追跡可能にする
- **段階導入**: 古典的画像処理から開始し、必要な場合だけ ML を追加する

## 3. 対象外

初期段階では以下を対象外とする。

- **標高推定**: 単眼航空写真から標高・カントは推定しない
- **完全無人生成**: 人間の確認なしで保存・GLB ビルドしない
- **任意の斜め写真**: 正射画像または上面画像を前提とする
- **物体生成**: 壁、フェンス、看板、建物、樹木は生成しない
- **画像の製品同梱**: 解析元画像のライセンス条件を越えて画像自体を出力へ含めない

## 4. 現行設計との対応

### 4.1 出力先

現行 `TrackDef` をそのまま利用でき、MVP ではスキーマ変更を不要とする。

- **幅**: `road.edges.step`, `road.edges.left`, `road.edges.right`
- **縁石**: `curbs[].startDist`, `endDist`, `side`, `width`, `stripeLength`
- **中心線**: 将来フェーズのみ `controlPoints`

`road.edges` は `road.width` と `road.widthProfile` より優先される。解析結果の適用後は既存の幅点ドラッグで修正できる。

### 4.2 座標規約

- **単位**: メートル
- **座標**: ENU、Y-up
- **水平軸**: `x = east`, `z = south (-north)`
- **接線**: `(tx, tz)`
- **右法線**: `n = (-tz, tx)`
- **左端位置**: `center - n * offsetLeft`
- **右端位置**: `center + n * offsetRight`

左右判定は全モジュールでこの規約を使用する。

### 4.3 標高との整合

現在の路面端標高は、`elevation.json` の `corridorHalfWidth` で取得した左右標高を、実際の左右オフセットまで線形外挿または内挿している。

自動抽出幅が `corridorHalfWidth` を越えると標高が外挿されるため、次を必須とする。

- **警告条件**: `max(offsetLeft, offsetRight) > corridorHalfWidth`
- **適用可否**: 警告して適用は可能とするが、自動保存はしない
- **推奨処理**: GSI 等の再取得可能データでは、十分なコリドー幅で標高を再取得する
- **Imported 標高**: 自動上書きせず、外挿区間を明示する

## 5. 段階構成

### Phase 0: 評価データと入力仕様

- **画像選定**: 利用条件を確認した富士・Barber 相当の異なる2コース以上
- **正解データ**: 左右端を複数地点で人手計測
- **縁石正解**: 開始・終了・左右を人手記録
- **評価スクリプト**: 解析結果と正解値の誤差を出力

### Phase 1: 既知中心線からの幅候補

- **入力**: 既存中心線と地理参照済み画像
- **出力**: 左右オフセット、左右信頼度、診断情報
- **UI**: プレビュー、信頼度しきい値、適用、破棄、Undo
- **実装方式**: TypeScript の決定論的画像処理

### Phase 2: 縁石候補

- **入力**: 画像と現在または提案中の舗装端
- **出力**: `CurbSpanDef` 候補と信頼度
- **UI**: 区間単位の採用・除外・編集
- **制限**: MVP は現行メッシュが表現できる赤白縁石を主対象とする

### Phase 3: ユーザー支援セグメンテーション

- **入力**: 路面上・路面外への数クリックまたはブラシ指定
- **処理**: 道路領域マスクを補正し、幅抽出へ渡す
- **候補技術**: ONNX Runtime Web、SAM 系モデル、専用軽量セグメンテーションモデル
- **導入条件**: Phase 1 の精度が不足し、モデルサイズとライセンスを許容できる場合

### Phase 4: 画像からの中心線候補

- **処理**: 道路マスクの骨格化、グラフ化、主ループ選択、枝刈り、平滑化、制御点簡略化
- **必須UI**: 中心線制御点の編集、分岐選択、周回方向選択
- **注意**: 中心線変更時は幅・縁石・標高の弧長対応が変わるため、独立したトランザクションとして扱う

## 6. 入力画像

### 6.1 対応ソース

共通の `RasterSource` 抽象を設け、解析アルゴリズムを画像取得方法から分離する。

1. **地理参照画像**: JPEG/PNG と `satellite_meta.json` 相当の bbox メタデータ
2. **GSI タイル**: `origin` と対象範囲から必要タイルを取得
3. **ユーザー画像**: ファイル選択後、対応点で位置合わせ

MVP の優先順位は、地理参照画像、GSI タイル、手動キャリブレーション画像の順とする。

### 6.2 内部インターフェース

```ts
interface RasterSource {
  id: string;
  resolutionMetersPerPixel: number;
  sampleLocal(x: number, z: number): Rgb | null;
  containsLocal(x: number, z: number): boolean;
}
```

画像全体の保存場所や URL を解析ロジックへ渡さず、ローカル座標で画素を取得する。

### 6.3 地理座標から画素への変換

`origin` がある場合、まずローカル座標を緯度経度へ変換する。

```text
lat = origin.lat - z / 111320
lng = origin.lng + x / (111320 * cos(origin.lat))
```

Web Mercator bbox の画像では、緯度経度を正規化タイル座標へ変換する。

```text
mx(lng) = (lng + 180) / 360
my(lat) = (1 - asinh(tan(lat)) / PI) / 2
u = (mx(lng) - mx(minLng)) / (mx(maxLng) - mx(minLng))
v = (my(lat) - my(maxLat)) / (my(minLat) - my(maxLat))
px = u * (imageWidth - 1)
py = v * (imageHeight - 1)
```

画像外は `null` とし、端の画素へ暗黙にクランプしない。

### 6.4 手動キャリブレーション

地理情報のない正射画像では以下を提供する。

- **2点方式**: 回転、均一スケール、平行移動
- **3点以上**: アフィン変換と残差表示
- **不採用**: MVP では射影変換を必要とする斜め写真
- **確認**: 中心線を画像へ重ね、ユーザーが位置合わせを明示承認する

位置誤差1 mは幅誤差へ直接影響するため、キャリブレーション残差を解析信頼度とは別に表示する。

### 6.5 解像度基準

- **0.50 m/px以下**: 幅解析に適する。縁石は候補抽出可能
- **0.50〜1.00 m/px**: 幅解析は可能。縁石は低信頼扱い
- **1.00 m/px超**: 幅は参考値。縁石解析を既定で無効化
- **超解像画像**: 見た目の画素数ではなく、元画像の実効解像度を使用する

## 7. 幅抽出アルゴリズム

### 7.1 入力と出力

```ts
interface WidthAnalysisOptions {
  step: number;
  minOffset: number;
  maxOffset: number;
  candidateStep: number;
  smoothness: number;
  priorStrength: number;
  confidenceThreshold: number;
}

interface WidthProposal {
  step: number;
  left: number[];
  right: number[];
  confidenceLeft: number[];
  confidenceRight: number[];
  diagnostics: WidthDiagnostics;
}
```

既定値の初案は次のとおりとする。

- **解析間隔**: 2 m
- **探索範囲**: 左右それぞれ3〜20 m
- **候補間隔**: `max(0.25 m, 0.5 px相当)`
- **ハード制限**: 現行 Editor と同じ1〜30 m

### 7.2 前処理

解析対象は中心線から `maxOffset + margin` のコリドーだけとする。

- **色空間**: sRGB から Lab へ変換
- **勾配**: 法線方向の輝度勾配
- **局所統計**: 内側・外側の平均色、分散、テクスチャ量
- **無効領域**: 画像外、透過画素、取得失敗タイル

全画像へ重いフィルタを掛けず、必要断面をオンデマンドでサンプリングする。

### 7.3 断面候補

各中心線ステーションで左右独立に法線断面を走査する。各距離候補の証拠スコアは以下を組み合わせる。

- **境界勾配**: 候補位置を挟む輝度変化
- **色差**: 内側路面モデルと外側領域の Lab 色差
- **内側整合**: 中心線から候補までが概ね同じ路面特性を持つか
- **線・縁石証拠**: 高輝度線、赤白、高周波パターン
- **既存幅事前分布**: 現在値から過度に離れる候補への弱いペナルティ
- **無効ペナルティ**: 画像端、影、極端な局所ノイズ

中心線直上だけを路面色の正解にしない。前後数ステーションと中心から左右2 m程度のロバスト中央値を路面モデルとし、白線や車両の影響を抑える。

### 7.4 全周最適化

各断面の最大スコアを独立採用すると、白線、車両、影で幅が飛ぶ。左右それぞれについて動的計画法で全周経路を求める。

```text
objective = Σ evidence(i, offset_i)
          - λ1 Σ |offset_i - offset_(i-1)|
          - λ2 Σ excessiveSlope(offset_i, offset_(i-1))
          - λ3 Σ priorDistance(offset_i, current_i)
```

- **閉路**: 開始・終了の連続性を含む circular DP とする
- **開路**: 端点は wrap しない
- **急拡幅**: 完全禁止せず、画像証拠が強い場合に残す
- **左右独立**: 対称化しない

### 7.5 後処理

- **外れ値抑制**: 短い単発スパイクをロバスト中央値で除去
- **平滑化**: エッジ形状を失わない弱い平滑化
- **丸め**: 保存時のみ0.01 mへ丸め、解析内部は浮動小数のまま
- **継ぎ目**: 閉路の先頭・末尾を同じ条件で処理

### 7.6 信頼度

信頼度は「その画素が路面である確率」ではなく、候補を人間が採用できる程度の相対指標とする。

構成要素は以下とする。

- **候補余裕**: 採用候補と次点候補のスコア差
- **境界強度**: 色差と勾配の絶対強度
- **経路整合**: 周辺ステーションとの連続性
- **画像品質**: 解像度、欠損、局所コントラスト
- **左右妥当性**: 合計幅が設定範囲内か

`0..1` へ正規化し、次の3段階で表示する。

- **高信頼**: 緑。既定の一括適用対象
- **要確認**: 黄。ユーザー確認後に適用
- **低信頼**: 赤。現在値を維持するのが既定

## 8. 縁石抽出アルゴリズム

### 8.1 前提

縁石解析は舗装端候補の後に行う。幅候補をまだ適用していない場合でも、プレビュー中の端位置を入力にできるようにする。

現行 `CurbSpanDef` とメッシュは赤白ストライプを表現する。MVP では赤白縁石を主対象とし、単色、黄黒、青白などは将来の `style` 拡張候補とする。

### 8.2 特徴量

舗装端の内外を横切る細い帯をサンプリングする。

- **赤色応答**: Lab/HSV による赤の彩度・色相
- **白色応答**: 高輝度かつ低彩度
- **交互性**: 弧長方向の赤白または明暗反復
- **境界近接**: 推定舗装端から所定距離内に存在するか
- **形状連続性**: 進行方向へ細長く連続するか

### 8.3 区間化

- **ヒステリシス**: 高しきい値で開始し、低しきい値で継続
- **短区間除外**: 4 m未満を既定で除外
- **小ギャップ結合**: 画像欠損による短い途切れを結合
- **左右独立**: 左右別に区間化
- **閉路対応**: 先頭と末尾の同一縁石を結合

### 8.4 推定値

- **開始・終了**: 0.5 m単位へ丸める
- **幅**: 画像から十分な横断厚が取れる場合だけ推定し、それ以外は1.2 m
- **ストライプ長**: 周期が明瞭な場合だけ推定し、それ以外は4 m
- **信頼度**: 区間全体と開始・終了境界を別々に保持する

Editor へ渡す時点では `CurbProposal` とし、採用時にだけ `CurbSpanDef` へ変換する。

## 9. Editor UX

### 9.1 パネル

新しい「画像から推定」セクションを追加する。

- **画像ソース**: GSI、ローカル画像、登録済み参照画像
- **解像度**: m/px と品質判定
- **位置合わせ**: 状態、残差、微調整
- **解析対象**: 幅、縁石
- **基本設定**: 最小幅、最大幅、平滑度、信頼度しきい値
- **操作**: 解析、キャンセル、適用、破棄

高度な重みは通常UIへ出さず、「詳細設定」にまとめる。

### 9.2 状態遷移

```text
idle -> loadingImage -> ready -> analyzing -> preview
                                  |          |       |
                                  v          v       v
                                error     cancelled applying -> idle
```

- **非破壊**: `preview` までは `model.def` を変更しない
- **キャンセル**: Web Worker へ中断要求を送り、遅い結果を破棄する
- **適用**: `model.snapshot()` を1回だけ呼び、1 Undoで全解析結果を戻せるようにする
- **再解析**: 前の提案を破棄してから開始する

### 9.3 プレビュー

- **幅候補**: 左右線を信頼度で緑・黄・赤に着色
- **現在値**: 現在の端を細い別色で残す
- **差分**: 選択地点で現在値、提案値、差、信頼度を表示
- **低信頼区間**: 一覧からカメラ移動できるようにする
- **縁石候補**: 区間単位のチェックボックスと左右タグを表示

### 9.4 適用方式

次の3方式を提供する。

1. **高信頼のみ**: 高信頼点を採用し、未採用点は現在値を維持。境界は短いブレンド区間で接続
2. **すべて適用**: 全提案を適用し、人間が後から修正
3. **選択範囲のみ**: 弧長範囲を指定して適用

既定は「高信頼のみ」とする。保存は既存の保存ボタンで別操作とし、解析適用直後に自動保存しない。

## 10. 実装アーキテクチャ

### 10.1 コア

純粋ロジックを `src/image-analysis/` に置き、Editor と分離する。

```text
src/image-analysis/
  types.ts          入出力と診断型
  coordinates.ts    local / lat-lng / pixel 変換
  raster.ts         画素サンプリングと色変換
  widthEvidence.ts  断面候補スコア
  optimizeEdges.ts  開路・閉路の全周最適化
  confidence.ts     信頼度計算
  curbs.ts          縁石スコアと区間化
```

### 10.2 Editor 側

```text
editor/
  analysisController.ts  Worker、状態、適用処理
  analysisOverlay.ts     提案線と信頼度表示
  imageSources.ts        GSI、画像、メタデータのアダプタ
  analysisWorker.ts      バックグラウンド解析
```

既存 `main.ts` はUIイベント接続、`model.ts` は提案適用のトランザクションだけを担当する。

### 10.3 実行場所

MVP はブラウザ内 Web Worker とする。

- **利点**: 画像を外部サービスへ送らない
- **利点**: Node/Python/ネイティブ依存を追加しない
- **利点**: パラメータ変更後すぐ再解析できる
- **制約**: Cross-Origin画像は直接Canvas解析できない場合がある

GSI タイル等は、CORS が保証されない場合に限り Vite の同一オリジン・キャッシュ経由で配信する。本番配布形態を決めるまでは開発サーバー専用APIとする。

### 10.4 ML 拡張

ML は `RasterSource` から道路・縁石確率マスクを生成する別レイヤーとし、幅の幾何処理は共通化する。

```text
image -> optional semantic model -> probability masks
      -> geometric edge optimizer -> WidthProposal / CurbProposal
```

これにより、古典処理とML処理を同じ評価データで比較できる。

## 11. 永続化と再現性

`track.json` は採用済み形状だけを保持する。未採用提案と画像情報を混在させない。

必要に応じて `analysis-session.json` を任意保存する。

```ts
interface AnalysisSession {
  version: 1;
  trackName: string;
  sourceId: string;
  sourceSha256?: string;
  effectiveResolution: number;
  centerlineFingerprint: string;
  options: WidthAnalysisOptions;
  widthProposal?: WidthProposal;
  curbProposals?: CurbProposal[];
  createdAt: string;
  analyzerVersion: string;
}
```

- **画像本体**: セッションへ埋め込まない
- **絶対パス**: 保存しない
- **中心線指紋**: 中心線変更後の古い提案適用を防ぐ
- **解析バージョン**: アルゴリズム変更時の比較に使う

## 12. バリデーション

解析開始前に以下を検査する。

- **中心線**: 2点以上で総延長が正
- **画像範囲**: 中心線コリドーの95%以上をカバー
- **解像度**: 有限かつ正
- **位置合わせ**: ユーザー承認済み
- **探索幅**: `1 <= minOffset < maxOffset <= 30`
- **解析間隔**: 正で、結果配列長が Editor の規約と一致

提案適用前に以下を検査する。

- **配列長**: 左右と信頼度が一致
- **数値**: `NaN`, `Infinity`, 負値がない
- **閉路**: 先頭・末尾付近に異常な不連続がない
- **合計幅**: 許容範囲内
- **標高コリドー**: 外挿区間を警告
- **中心線指紋**: 解析開始時と一致

## 13. テスト計画

### 13.1 単体テスト

- **座標変換**: bbox四隅、中心、画像外、南北方向
- **左右規約**: 直線・曲線で左右画素位置が正しい
- **幅抽出**: 一様幅、非対称幅、段階的拡幅
- **閉路最適化**: 開始位置に依存せず継ぎ目が滑らか
- **ノイズ耐性**: 車両点、白線、影、欠損タイル
- **隣接道路**: ピットロードが探索範囲内にあるケース
- **縁石区間**: 短区間除外、ギャップ結合、閉路結合
- **信頼度**: 明瞭境界と曖昧境界の順序が正しい

合成画像を生成して期待値をメートル単位で検証し、外部画像をCIへ含めない。

### 13.2 統合テスト

- **Editor適用**: 解析前は非変更、適用後に `road.edges` が更新
- **Undo**: 1回で幅と縁石の適用前へ戻る
- **保存**: 既存APIで保存・再読込できる
- **GLB**: 路面と縁石ビルドが成功する
- **キャンセル**: 遅れて返った Worker 結果を適用しない

### 13.3 実画像評価

正解地点をコーナー、直線、影、ランオフ、ピット隣接へ分散する。

初期の目標値は以下とし、Phase 0 で現実的な値へ更新する。

- **左右端 MAE**: 高信頼点で0.75 m以下
- **左右端 P90**: 高信頼点で1.50 m以下
- **重大誤差**: 3 m超が全点の2%未満
- **高信頼カバレッジ**: 全周の70%以上
- **縁石 Precision**: 0.80以上を優先
- **縁石区間 IoU**: 0.60以上
- **処理時間**: 4.5 kmコースで10秒以内を目標

縁石は見逃しより誤追加のコストが高いため、Recall より Precision を優先する。

## 14. リスクと対策

| リスク | 影響 | 対策 |
|---|---|---|
| 画像位置ずれ | 左右幅が系統的に誤る | 重ね合わせ承認、微調整、残差表示 |
| 影・樹木 | 境界の途切れ | 全周最適化、低信頼表示、現在値維持 |
| 白線を舗装端と誤認 | 幅が狭くなる | 線幅特徴、外側色差、前後連続性 |
| ランオフもアスファルト | 舗装端が広すぎる | 既存幅事前分布、ユーザー範囲指定、将来セグメンテーション |
| ピット・サービス道路 | 別道路へジャンプ | 中心線法線の探索上限、平滑化、低信頼化 |
| 縁石が数画素 | 区間誤検出 | 解像度ゲート、候補扱い、Precision優先 |
| 標高コリドー超過 | 端標高が外挿 | 適用時警告、標高再取得 |
| 画像ライセンス | 配布・派生利用上の問題 | ソース別条件確認、画像非同梱、出典記録 |
| MLモデル肥大化 | 起動時間・配布サイズ増加 | 古典処理を先行、必要時のみ任意導入 |

## 15. 中心線自動生成時の追加設計

中心線生成は幅・縁石とは破壊範囲が異なるため、別機能として扱う。

### 15.1 処理

1. **道路マスク**: 自動またはユーザープロンプトで生成
2. **形態処理**: 小穴、車両、影による欠損を補正
3. **主成分選択**: ユーザーがメインコースをクリック
4. **骨格化**: 距離変換と medial axis
5. **グラフ化**: 分岐点、端点、閉路を抽出
6. **主ループ選択**: ピット・アクセス路を枝として分離
7. **平滑化**: 画像ノイズを抑制
8. **簡略化**: RDP等で制御点化し、Catmull-Rom再生成結果を検証
9. **方向指定**: 進行方向をユーザーが確定

### 15.2 既存データへの影響

中心線を変更すると弧長と法線が変わる。

- **`road.edges`**: 古い中心線へ紐づくため、そのまま再利用しない
- **`curbs`**: `startDist/endDist` が別位置を指すため再投影が必要
- **`elevation.json`**: サンプル位置と総延長が変わるため再生成が必要
- **`refs.json`**: ローカル座標の参照線自体は保持可能

適用前に旧形状をワールド座標ポリラインへ変換し、新中心線へ再投影する移行案をプレビューする。それでも標高は再取得を原則とする。

## 16. 推奨する最初の開発単位

Phase 1 を次の4つに分割する。

1. **座標・RasterSource**: 富士相当画像上で中心線の断面画素を正しく取得
2. **オフライン幅評価**: UIなしで `WidthProposal` と誤差レポートを生成
3. **Editorプレビュー**: 信頼度色、現在値との差、低信頼区間一覧
4. **安全な適用**: 高信頼のみ・全適用・Undo・標高警告

縁石実装は幅の評価結果が目標を満たしてから開始する。中心線生成はさらに後段とする。

## 17. 実装開始前の決定事項

- **最初の画像ソース**: GSI タイル、既存地理参照画像、ユーザー画像のどれを基準にするか
- **評価コース**: 少なくとも2コースと、その画像利用条件
- **正解作成量**: 全周か、代表100〜200地点か
- **対象縁石**: 赤白だけか、他色・単色も必要か
- **オフライン要件**: 外部タイル取得を許可するか
- **ML許容範囲**: モデルサイズ、ライセンス、GPUなし実行時間
- **幅の意味**: 白線内、舗装端、縁石内端のどこをコース端と定義するか

最後の「幅の意味」は画像上の正解作成前に固定する。推奨定義は、**走行可能な主舗装面の端。ただし縁石は舗装幅へ含めず、縁石の内端を `road.edges` とする**。

## 18. 採用判断

本機能は現行データモデルへ無理なく追加できる。最も費用対効果が高いのは、画像だけから全形状を生成する方式ではなく、既存中心線を制約として左右端を全周最適化し、信頼度付きで人間へ提示する方式である。

Phase 0 で実画像の誤差分布を確認し、Phase 1 の古典処理が目標精度へ届かない区間だけ、ユーザー支援セグメンテーションまたは ML を追加する。
