# 境界線ファーストのトラック編集構想

## 結論

境界線をユーザーが直接編集する思想は、トラック形状をマウスで調整するUIとして適している。

ただし、次のように編集表現と内部表現を分離する。

- ユーザーは左右の境界線を直接編集する
- 中心線は内部計算用の軸として保持または派生する
- 密な点列は編集用制御点ではなく、メッシュ生成用の出力とする

「外側の線1本だけ」を形状の正とする設計は不足する。周回路面はドーナツ状の領域なので、最低でも左右端、言い換えると外周と内周の2本の境界線が必要になる。

## 現行設計との関係

現在の `track-creator` は、次の構造を採用している。

- Catmull-Rom曲線で表現した中心線
- 中心線から左右の舗装端までの距離
- 中心線の弧長を基準にした標高、縁石、メッシュ生成

関連箇所:

- `src/types.ts`: `controlPoints` と `road.edges`
- `src/mesh/stations.ts`: 中心線、左右幅、標高からステーション列を生成
- `editor/tools.ts`: 左右エッジ点のドラッグ編集と中心線のなぞり直し

富士の現行データは、おおよそ次の密度になっている。

- 中心線制御点: 652点
- 左右エッジ: 各2,280点
- エッジサンプル間隔: 2m

2,280点のエッジは、すべてを人間が管理する編集用制御点としては多すぎる。これらは、少数の編集用アンカーから生成されるサンプル点として扱う方がよい。

## 推奨する3層構造

### 1. 編集層

左右境界を、少数のアンカーポイントと線分で表現する。ユーザーが直接操作するのはこの層だけとする。

編集層が持つ情報の例:

- アンカーの位置
- 直線または曲線の区間種別
- 角、滑らか、自動接線などのアンカー種別
- フィレット半径
- 手動確定済みか、画像解析からの候補か

### 2. 計算層

左右境界から、メッシュ生成に必要な内部情報を求める。

- 進行方向
- 中心軸
- 弧長 `s`
- 左右対応点
- 左右幅
- 法線方向
- 横断勾配と標高参照位置

中心線はユーザーに常時表示する必要はないが、縁石、標高、UV、オブジェクト配置、Blender連携の基準として内部には必要になる。

### 3. 出力層

編集形状を1～3m程度の間隔でリサンプルし、既存パイプラインが利用できる形式へ変換する。

- `road.edges.left/right`
- 道路ステーション列
- 縁石区間
- 標高サンプル
- GLBメッシュ
- Blender用の中心軸と幅情報

境界線を編集用ソース、現在の密な配列をコンパイル結果と位置付ける。

## 操作設計

提案されている次の操作は、境界線編集と相性がよい。

- 線分上をクリックしてアンカーを追加する
- アンカーをドラッグして移動する
- 選択したアンカーを削除する
- 選択区間を直線へ変換する
- 選択区間を滑らかな曲線へ変換する
- 接続した直線の角を半径指定で丸める
- 選択範囲だけを局所的に平滑化する
- 左右境界間を塗りつぶし、実際の路面領域を常時表示する

曲線操作は、最初から複雑なハンドルを常時表示するより、次の3種類程度から始める方が扱いやすい。

- 角
- 自動スムーズ
- 手動スムーズ

「直線を少し丸める」操作は、全体へ平滑化フィルターを掛けるのではなく、フィレット半径を指定する方式が適する。一般的な平滑化は、意図した直線や画像上の境界を内側へ縮める可能性がある。

## 制御点とサンプル点の分離

編集用の制御点と、メッシュ生成用のサンプル点を明確に区別する。

### 制御点

- 人間が追加、移動、削除する
- 形状上の意味がある地点だけに置く
- 直線と曲線の境界、コーナーの入口と出口などを表す
- 安定したIDを持つ

### サンプル点

- 制御点から自動生成する
- 曲率に応じて必要な密度へ増減する
- ユーザーは原則として削除しない
- GLB、Blender、画像解析、標高計算へ渡す

現在の `road.edges` はサンプル点に相当する。

## 重要な課題

| 課題 | 想定される問題 | 対応方針 |
|---|---|---|
| 境界線が1本だけ | 幅と反対側の形状が決まらない | 左右2本を編集対象にする |
| 左右点の対応 | 不適切な対応で路面がねじれる | 中心軸の横断面単位で対応付ける |
| ヘアピンや近接区間 | 別の区間へ投影・吸着する | 前後連続性と探索範囲で制約する |
| 境界線の交差 | 幅ゼロ、裏返った三角形が発生する | 最小幅、交差、三角形反転をリアルタイム検査する |
| 制御点の削除 | 周辺形状が予想以上に変化する | 変更前後と最大変位をプレビューする |
| 閉ループの継ぎ目 | スタート地点で折れや段差が発生する | 位置と接線の連続性を検査する |
| 中心線の変更 | 幅、縁石、標高の弧長対応がずれる | 再投影または再生成を行う |
| ピットレーンと分岐 | 単純な左右2境界で表現できない | 本線とは別サーフェスとして扱う |
| 画像上の境界定義 | 白線、舗装端、縁石、ランオフが混同される | レイヤーごとの境界定義を固定する |

## 中心線変更時の整合性

現行の中心線なぞり直し処理は、中心線変更後も既存の `road.edges` と `curbs` を残している。

しかし、これらは旧中心線の弧長と法線を基準にしているため、中心線変更後にそのまま利用することは安全ではない。

中心線を変更した場合は、最低でも次を行う必要がある。

- 旧左右境界をワールド座標へ変換する
- 新しい中心線へ左右境界を再投影する
- 縁石の開始・終了位置を再投影する
- 標高サンプルを再取得または再対応付けする
- 変更前後の差分を保存前にプレビューする

中心線変更は、通常の幅編集とは別のトランザクションとして扱う。

## 走行面とランオフの分離

富士のように舗装ランオフやピットレーンが存在する場合、最外周のアスファルト境界だけでは本線の形状を決められない。

次のような複数レイヤーが必要になる。

| レイヤー | 意味 |
|---|---|
| `ROAD` | 白線内または走行可能な主舗装面 |
| `RUNOFF/EDGE` | ランオフを含むアスファルト外周 |
| `CURB` | ROAD端に付随する縁石帯 |
| `PIT` | ピットレーンなど本線から分岐する舗装面 |

最外周だけを `ROAD` とすると、舗装ランオフやピットを本線幅として取り込み、幅が数十メートルになる可能性がある。

## Blender連携上の注意

現在の標準的なBlender連携は、左右幅を合計して中心線カーブの幅へ変換する。その場合、左右非対称な形状は失われる。

左右非対称を再現するには、次のいずれかが必要になる。

- 左右境界の中点へ中心軸を移動し、合計幅を適用する
- Blender側で左右レールを直接使って道路メッシュを生成する

前者は既存のTrack Toolsへ接続しやすいが、一方の境界に誤検出があると中心軸全体まで移動する。両側が確認済みの区間だけ再センタリングする、移動量を制限する、変更をプレビューするなどの保護が必要になる。

後者は左右境界を忠実に再現できるが、Blender側の生成処理を拡張する必要がある。

## 推奨する段階的な導入

### Phase 1: 現行中心線を利用した境界編集

- 現行中心線は固定する
- 左右境界へ少数の編集アンカーを導入する
- 直線、曲線、フィレット操作を提供する
- 編集結果を現在の `road.edges` へ焼き込む
- 既存の画像解析、GLB生成、Blender連携を維持する

この段階で、マウスによる境界修正という主要な操作性を検証できる。

### Phase 2: 左右境界から中心軸を派生

- 左右境界を編集形状の正とする
- 左右点の対応を求める
- 中点列から内部中心軸を生成する
- 既存の縁石と標高を再投影する
- 差分確認後にだけ中心軸を更新する

### Phase 3: 複数舗装レイヤー

- 主走行面
- ランオフ
- ピットレーン
- 縁石
- 路肩やグラベル

これらを独立した境界または帯として扱い、Blenderへ渡す。

## 採用判断

境界線ファーストのマウス操作は採用する価値が高い。

ただし、採用条件は次のとおりとする。

- 単一の外周線ではなく、左右境界を扱う
- 制御点と出力サンプル点を分離する
- 中心線を内部の弧長軸として残す
- 中心線変更時は幅、縁石、標高を再投影する
- 走行面とランオフを別レイヤーにする
- 交差、最小幅、閉路継ぎ目を自動検査する
