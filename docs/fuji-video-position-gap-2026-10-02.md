# 富士：車載動画とビューワー表示の位置ずれ（原因と対策方針）

## 要旨

車載動画（AiM SmartyCam）とビューワーの「走行位置のずれ」は、1つの原因ではなく、**時間方向・表示モデル・横方向**の3系統が重なって見えている。今回、未使用だった7/30の車載動画も加えて、動画を基準に切り分けた。

1. **最大の原因は7/30の時刻ずれ（約0.51秒）。** GPS位置と、ロガー時計で記録したチャンネル（スロットル・ブレーキ・ステア・ギア・内蔵G）の時刻が合っていない。ロガー時計側が約0.5秒早い。7/29はほぼ0秒（+0.01秒）。
   - 次の3つの方法で同じ結論になった：内蔵GとGPS由来加速度の相互相関、ブレーキ開始からGPS減速開始まで（39区間）、動画に焼き込まれたペダル表示と記録値の照合。
   - ビューワーでは、7/30だけブレーキ表示・軌跡の赤・ブレーキランプ・ステア・HUDが、車の位置より**約25m（高速域で30〜36m）手前**で反応する。
   - 9/22時点では「見かけ遅延」として不採用にしていた。今回、日による差と動画の実時間表示で裏づけが取れたので、**補正対象に改める。**
2. **比較するときの時刻基準でも数mずれる。**
   - ビューワーの時刻は、真のラップ開始ではなく最初の10Hz標本を0秒としている。差のδは7〜97msで、使われていない。このため動画のラップタイマーと同じ時刻に合わせると、車は最大5m前に出る。
   - 一方、動画の映像そのものに対しては、GPS位置が約0.2秒遅れて見える（両日同程度）。オーバーレイの表示遅れ約0.09秒を含む。
   - 過去資料の「動画秒＝L3＋458.9秒」はOpenCVのシーク基準である。PTS基準（ffmpeg）とは1.0秒（約50m）違う。
3. **ビューワーの見せ方でも、同じ位置がずれて見える。**
   - 再生中は向きが140msの一次遅れで追従するため、ヨー角誤差は95パーセンタイル（p95）で約4°、ダンロップでは最大7.6°。前方20〜50mの景色が1.4〜3.5m横にずれる。
   - コックピット視点は、高さ0.78m・右0.28m・水平視野89°・下向き0°である。SmartyCamは中央・高さ約1.25m・下向き13〜15°・水平視野約95°で、広角の歪みもある。
4. **横方向の残差は、引き続き未確定。** ラップ単位の平行移動（9/22）で、道路外への逸脱は大きく減った。ただし「道路内のどこを走ったか」は道路制約だけでは一意に決まらない。

**対策の優先順位：**
- **P1**
  - 7/30の時刻を整合させる（前処理でロガー時計チャンネルをGPS基準へ約+0.51秒寄せ、自動検査を追加する）
  - 動画同期の手順をPTS基準へ統一する
- **P2**
  - ビューワーの時刻を真のラップ時刻にする
  - 再生中の向きの遅れを減らす
  - SmartyCam相当の比較用カメラを用意する
- **P3**
  - 動画から横位置を測る（左右の白線の傾きの比を使う方法）。測れた場合に限り、平行移動の精度向上へ使うか判断する

GPSの絶対位置を地点ごとに合わせ込む方法や、時間とともに変わる補正は、今回も採らない。

## 「ずれ」を3方向に分ける

| 方向 | 見え方 | 主な原因（今回の判定） |
|---|---|---|
| 時間（進行方向） | 動画では1コーナーのブレーキ板付近なのに、ビューワーでは手前／先にいる。ブレーキやスロットルの表示と車の動きが合わない | 7/30のチャンネル時刻ずれ0.51秒。比較時の基準差（δ、オーバーレイ遅れ、OpenCV基準） |
| 見た目（視点・向き） | コックピット視点で景色の位置や道路の見え方が動画と違う | 再生中の向きの遅れ、カメラの位置・高さ・下向き角・画角・歪みの違い |
| 横（道路内の位置） | 縁石からの距離や道路端への寄り方が違う | セッションごとのGPS偏りの残差（L1で大半は補正済み、道路内の位置は未確定） |

## 今回の証拠と時刻合わせ

- **使った動画：** 7/29 `SCHD0613.MOV`（4周）と7/30 `SCHD0624.MOV`（6周。従来未使用）。いずれもユーザー提供のローカル参照用で、公開配布不可。フレームは保存していない。
- **時刻基準：** ffmpegのPTS。各周の10/50/90%でオーバーレイのラップタイマーを読み、周回ごとに動画上の真のラップ開始時刻を決めた（[タイマー読取](../artifacts/video-position-gap-2026-10-02/video-timer-reads.json)）。
  - 7/30は6周を通して±0.03秒以内で一致した（L5のみ+0.09秒）。
  - 7/29も周回内の一致は良いが、基準が旧資料と1.0秒違う（次の点）。
- **OpenCVのシークとの差：** 7/29の動画でOpenCVの `CAP_PROP_POS_MSEC` で219.7秒・513.9秒へシークすると、要求より30フレーム（1.000秒）後のフレームが返る（タイマー0:50.02と0:49.02、0:54.99と0:53.99）。
  - 旧資料の「動画秒＝L3＋458.9秒」はOpenCV基準の値である。PTS基準ではL3開始が約459.89秒になる。
  - 旧資料の内部ではタイマー読取と同じ基準で整合している。ただし、別の基準で取り出したフレームと混ぜると、1秒（高速域で約50m）ずれる。
- **ラップの区切り：** 両日10周とも、ラップ開始時点の元GPSは道路上の同じ地点（138.03〜138.08m）にある。ラップ境界と動画タイマーは、GPSの時刻基準で動いている。

## 原因1：7/30のGPSとロガー時計チャンネルの時刻ずれ

`accx/accy` はロガー内蔵加速度計（InlineAcc/LateralAcc）、`aps/brake/steer/gear` はECU（CAN）である。どちらもロガー時計で記録されている。GPS（位置・GPS車速・ラップ境界）だけが別の時刻系で記録されている。

| 指標 | 7/29（wet） | 7/30（dry） |
|---|---|---|
| 内蔵G vs GPS由来加速度の時刻差（前後・横、各周、3次補間） | 中央値 +0.014秒（−0.08〜+0.07） | **中央値 −0.507秒（−0.54〜−0.44）**、L1→L6で約0.07秒ゆっくり変化 |
| ブレーキ開始 → GPS速度の減速開始 | +0.10秒（+3.8m）、29区間 | **+0.64秒（+24.6m）**、39区間。高速制動では+30〜36m |
| ブレーキ開始 → 内蔵Gの減速開始 | +0.08秒 | +0.08秒（ECUと内蔵Gは両日とも整合） |
| 動画に焼き込まれたペダル表示 vs 記録値（r=0.96〜0.99） | 表示が記録より +0.03〜0.19秒（中央値約0.09秒） | 表示が記録より **+0.55〜0.78秒**（中央値約0.63秒） |
| 動画ヨー（窓のオプティカルフロー）に対するGPS進行方向変化 | +0.04〜+0.38秒（中央値約0.19秒） | +0.17〜+0.33秒（中央値約0.24秒） |
| 動画ヨーに対する内蔵横G／速度 | +0.17〜+0.34秒（中央値約0.22秒） | **−0.20〜−0.34秒（中央値約−0.27秒）** |

数値は [channel-timing-audit.json](../artifacts/video-position-gap-2026-10-02/channel-timing-audit.json) による。

**判断：**
- 同じ車、同じセンサー、同じ動画カメラで、ロガー時計側のチャンネルだけが日によって約0.5秒ずれている。ECUと内蔵Gは両日とも互いに整合しており、GPSとの関係だけが変わっている。
- 走行中にリアルタイムで表示されたペダルとラップタイマーの関係は、両日とも同じ程度の遅れだった。0.5秒の差は記録ファイル上だけにある。
- 7/30の値はセッション内で約100ppmずつ変化している。これは2つの時計の対応づけが、セッションの開始時に約0.5秒ずれて決まったことと整合する。
- 9/22にGPSと車輪速度を比べた「見かけ遅延」は、タイヤの滑りや校正の影響を区別できなかった。今回は、日による差（同一条件で0.5秒）、物理的に同時に起きる量（加速度と加速度）、動画の実時間表示の3点で裏づけが取れたので、補正対象に改める。

**ビューワーへの影響（7/30のみ）：**
- **車の位置より約0.5秒早く反応する：** HUDのスロットル・ブレーキ・ギア・ステア・G、テレメトリーパネル、前輪の舵角、ブレーキランプ（ブレーキ3%超）、軌跡の赤色（ブレーキ5%超）、シネマティック演出の入力
- **影響を受けない（GPS由来）：** 車の位置・向き、ミニマップ、軌跡の形、車速、距離・デルタ

**限界：**
- 動画とログの対応づけはロガー由来のタイマーやチャンネルを経由するため、「GPSとロガー時計のどちらが絶対時刻に対して正しいか」はこの資料だけでは決められない。
- ただしビューワーはラップ（GPS時刻基準）で再生し、動画もラップタイマーで合わせる。このため、**ロガー時計側のチャンネルをGPS基準に寄せる補正**が、両日・動画のすべてと整合する。

## 原因2：比較するときの時刻基準

- **δ（最初の標本の遅れ）：** ビューワーの時刻（HUD TIMEとシークバー）は `lap.t` で、最初のGPS標本が0秒である。真のラップ開始からの差 `first_sample_after_lap_start_seconds`（7〜97ms）は、`src/` のどこでも使われていない。
  - 動画のタイマーと同じ値に合わせると、車は δ×速度 だけ前に出る。メインストレートでは7/29で0.3〜2.5m、7/30で0.7〜5.0m。
  - ゴーストのデルタにも、2周のδの差が入る。
- **映像そのものとの差：** ラップタイマーで合わせた場合、GPS位置は映像のヨーより約0.2秒遅れる（両日同程度）。内訳はおおむね次のとおり。
  - オーバーレイ表示の遅れ（7/29のペダル表示で約0.09秒）
  - 車体の向きと進行方向の物理的な時間差
  - 両日でほぼ一定なので、データの誤りというより「比較の同期オフセット」として扱う。180km/hで約10m、60km/hで約3mに相当する。
- **基準の混在：** 前節のとおり、OpenCVとPTSの1.0秒差。

## 原因3：ビューワーの見せ方

- **再生中の向きの遅れ：**
  - 再生中、車の姿勢は目標姿勢へ時定数140msで追従する（`src/engine/ReplayScene.ts:772-777`）。ヨーレート×0.14秒だけ向きが遅れる。
  - 全10周13,826点で見ると、ヨー角誤差の中央値1.07°、p95 3.96°、最大7.59°（ダンロップの切り返し、約2.81〜2.86km）。
  - コックピット視点はこの向きを使うため、前方20mで0.37〜1.38m、50mで0.93〜3.46m（中央値〜p95）、景色が横にずれて見える。
  - 停止中やシーク時は即時に追従する。進行方向推定の±0.6秒の弦（`src/replay/interpolation.ts:453`）による誤差は、p95で0.77°と小さい。
- **コックピットカメラの違い**（`src/engine/cameras/cameraMath.ts:7-10`）：
  - ビューワー：GPS点から右0.28m・後0.55m・路面上0.78m、縦視野58°（水平約89°）、地平線は画面中央
  - SmartyCam：座席後方の天井付近、ほぼ中央、高さ約1.25m、下向き13〜15°（地平線はy≈205/720）、水平視野約95°、たる型歪みあり
  - 横位置の違いで、車が0.28m右に寄ったように見える。高さの違いで、ビューワーの20m先の路面が、動画では約32m先の画面行に相当し、遅れて見える。視野の違いでは逆に、約12%近く（前に）見える。
  - SmartyCamに相当するカメラモードは無い。
- **車体の姿勢：** ブレーキ時のダイブや車体のロールは描かない。縦方向の見え方の差は、主に目の高さと下向き角による。

## 原因4：横方向のGPS残差（既知、未確定）

9/22の結論は変わらない。
- セッションごとのGPS偏り（7/29と7/30で4.821m差）は、ラップ単位の平行移動で道路に整合させてある。
- 「道路内のどの位置を走ったか」は道路制約では決まらない。過去の映像からの横距離の概算は、カメラ高さを仮定していたため撤回した。
- 7/30の動画は今回初めて同期した。横位置の独立検証にも使える。

## 対策方針

| 優先 | 対策 | 内容 | 完了条件 |
|---|---|---|---|
| P1 | 7/30のチャンネル時刻整合 | 前処理（`pipeline/build_race.py`）に、セッション単位の「チャンネル時刻整合」を追加する。<br>・内蔵GとGPS由来加速度の相互相関から、周回ごとの時刻差Δ（7/30は約−0.51秒、線形変化を許す）を推定する<br>・ロガー時計チャンネルを t+Δ でサンプリングし直す<br>・GPS・ラップ境界・tは変えない<br>・メタにΔ・相関・手法を記録する<br>・再生成後に `register_gps_to_track.py` を再実行する（位置は不変だがラップのSHAが変わるため） | 全周で内蔵G対GPSが|Δ|<0.05秒。ブレーキ→GPS減速が7/29と同程度（約0.1秒）。補正の検証成功。Chromeでブレーキの赤とGPS減速の位置が一致 |
| P1 | 時刻ずれの自動検査 | 全セッションのビルド時に内蔵G対GPSの時刻差を計算し、|Δ|>0.05秒なら失敗または警告にする | 7/29は通過、修正前の7/30は検出、修正後は通過 |
| P1 | 動画同期手順の統一 | 動画の時刻はPTS（ffmpeg）かフレーム番号で扱う。周回ごとのタイマー読取をJSONに残す。OpenCVの時間指定シークは使わない。比較ツールでは映像に対するGPSの約0.2秒も同期オフセットとして明示する | 任意の3時刻で、タイマー値とビューワー時刻が±0.05秒で一致 |
| P2 | ビューワーの時刻を真のラップ時刻に | 表示時刻とデルタの基準を `t + first_sample_after_lap_start_seconds` にする（データの t は変えず、表示・比較時に加える） | 動画タイマーと同じ時刻で、メインストレートの前後差がδ由来で生じない |
| P2 | 再生中の向きの遅れを減らす | 姿勢の時定数を小さくする、または目標を140ms先読みする。コックピット視点ではヨーを平滑化しない | 再生中のヨー角誤差がp95で1°未満 |
| P2 | 動画比較用カメラ | SmartyCam相当（中央・高さ約1.25m・下向き約14°・水平視野約95°、可能なら歪みも）のプリセットを用意する。値は動画のフレームから校正する | 直線区間で、道路の消失点と左右の白線の位置が動画と数px以内で重なる |
| P3 | 動画から横位置を測る | 左右の白線の傾きの比を使う。路面上の2線の傾きはカメラ高さと焦点距離で同じ比率になるため、比を取ると横位置だけが残る。<br>・歪みは直線物（ロールバー、長い白線）で校正する<br>・直線区間に限ってロールの影響を抑える<br>・7/29と7/30の複数周で、補正後の横位置と比べる | 地点ごとの残差の平均と、ばらつき・時間変化を報告する。平行移動の改良に使うかは、その結果で判断する |

**採らないこと：**
- 地点ごとの手合わせ、GPS位置への時間変動補正（L2）
- 動画とGPS位置の約0.2秒をGPS座標側へ足すこと（同期オフセットとして扱う）
- 原因1の修正でGPSの緯度経度やラップ境界を動かすこと

## 検証と再現

- 再現：
  - `pipeline/.venv-sr/Scripts/python.exe scripts/quality/audit-fuji-channel-timing.py`（データのみ）
  - `--wet-video <7/29 SCHD0613.MOV> --dry-video <7/30 SCHD0624.MOV>`（動画の監査も行う。ローカルの原資料が必要）
- 出力：[channel-timing-audit.json](../artifacts/video-position-gap-2026-10-02/channel-timing-audit.json)、[video-timer-reads.json](../artifacts/video-position-gap-2026-10-02/video-timer-reads.json)。フレーム画像は保存していない。
- ローカルのビューワー（5199）で、富士7/29 L3の補正が有効で検証済み（`verified=true`）であることを確認した。補正入力のSHA検査（`verify-fuji-gps-handoff.py`）は合格した。
- 縦方向のオプティカルフローでピッチと減速を比べる試みは、相関が弱かった（r=0.1〜0.35）ため証拠に使っていない。
- ビューワー側の数値（向き誤差、カメラの値、チャンネルと表示の対応）は、コード読取と全10周の再計算による。ブラウザで表示を変更した検証はしていない。

## 未解決

- 7/30の0.5秒が、ロガー内部でGPS時刻と自分の時計を対応づける段階で生じたのか、ほかの経路なのかは特定していない。AiM内部の仕様が必要になる。
- 横方向の残差の大きさ（原因4）は、P3の測定までは数値で示せない。アンテナ位置・カメラの実測が無いことの影響も残る。
- 上の対策は、どれも実装していない（今回は調査と方針まで）。
