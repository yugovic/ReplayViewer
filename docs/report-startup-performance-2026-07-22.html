ReplayViewer 起動パフォーマンス実測レポート

対象: Fuji（?track=fuji&race=fuji_aim_01、ユーザーモード） · 計測日 2026-07-22 · Playwright(Chromium) · Vite devサーバ(:5199)

要旨

  • 起動の体感遅延を支配しているのは1ファイル、satellite_shizuoka.jpg（29.76 MB）。地上（衛星）テクスチャで、これがダウンロード完了するまで地面はフォールバック表示のまま。ダウンロードだけで 約2.0秒（cold）、しかも 読み込み開始が起動から約1.5秒後（JSONの直列依存待ち）なので、地面が正しく描かれるのは 起動から約3.5秒後（cold）。
  • アプリ全体の初期転送量は約 41.6 MB。うち 約72%（29.76 MB）が上記1ファイル。次点は terrain.png 3.64 MB、JSバンドル約5 MB（dev限定・本番は圧縮で大幅減）、RX3_race.glb 1.46 MB、features3d.json 1.06 MB。
  • ローディング表示（スピナー）自体は約0.2秒で消える。onReady は最初の描画フレームで発火し、重いアセットの到着を待たない（ViewerCanvas.tsx:87）。つまり「起動が遅い」の実体は スピナーの時間ではなく、地面テクスチャのポップイン。
  • 朗報（懸念の否定）: scene.glb（40MB）/scene.mod.glb（56MB）、imagegen_trials（440MB, 91枚）、corridor_x2 SRタイル（141枚）、他の衛星バリアント（bing 等）は 起動時に一切ダウンロードされない（遅延/視錐台ゲート/プローブ無効化により回避済み）。実測でこれらの取得は0件。
  • 無駄な読み込み: ユーザーモードで OFF のレイヤーの資産が取得されている。最大は features3d.json（1.06 MB）（表示は showFeatures3d:false なのに常に fetch）。加えて dev の StrictMode 二重マウントで各種JSONが2〜4回取得される（本番では発生しない）。
  • 削減の第一候補は明確: 29MB衛星画像の軽量化（再圧縮/縮小/WebP・KTX2、または低解像プレースホルダ先行）で −18〜22 MB / −1.2〜1.5秒 が見込める。並行取得化でさらに −0.5〜1秒。

計測方法

  • Playwright(Chromium, headless, 1600×900) で ?track=fuji&race=fuji_aim_01 を開き、performance.getEntriesByType("resource"/"navigation") と page.on("response") で全リクエストの URL・転送量・開始/終了時刻を採取。スピナー消滅は .loading-screen 要素の消失で判定。networkidle + 4秒 静定後にスナップショット。
  • スクリプト: Temp/measure_startup.mjs / 集計: Temp/analyze.mjs / 生データ: Temp/startup-cold.json, Temp/startup-warm.json。cold=新規コンテキスト（ブラウザキャッシュ空）、warm=直後の再計測。
  • 注意（未検証事項）: 計測は Vite開発サーバで実施。本番ビルド（vite build+preview）ではJS転送量・圧縮・キャッシュ挙動・StrictMode二重実行が異なる。データアセット（衛星/terrain/glb/json）の傾向は本番でも同一だが、JS系の数値と二重fetchは本番非該当。本番previewでの再計測は未実施。
  • アプリ既定のトラックは barber（dataLoader.ts:4）で、Fuji はピッカー/クエリ選択時のみ。重量級アセットは Fuji 側なので Fuji を対象とした。

無駄な読み込み（コード根拠つき）

1. features3d.json（1.06 MB）— レイヤOFFでも常に取得 検証済

  • ユーザープリセットは showFeatures3d: false（src/state/replayStore.ts:21）。3Dフィーチャ層は初期非表示。
  • しかし TrackBuilder.ts:953 loadFeatures3d(features3dUrl) は可視状態に関係なく必ず実行され、取得後に features3dGroup.visible = features3dVisible を適用（表示だけ後で切るが、fetchは走る）。
  • 実測でも features3d.json を取得（cold/warmとも）。ユーザーモードでは 約1.06MBが丸ごと無駄。

2. OFFレイヤの小JSONも取得（road_edges / overlays / ac_overlay / features）検証済

  • showTrackLines:false・showAcOverlay:false（replayStore.ts:23-24）でも、overlays.json（TrackBuilder.ts:978）・road_edges.json（TrackBuilder.ts:882）・ac_overlay.json（ReplayScene.ts:227、可視性に無関係で常時 fetch）を取得。features.json(OSM) も TrackBuilder.ts:942 で常時取得（OSM層もOFF）。
  • 各々は数十KB以下で影響は小さいが、ユーザーモードでは論理的に不要。

3. StrictMode 二重マウントによる二重〜四重 fetch dev限定・本番非該当

  • src/main.tsx:7 の <StrictMode> により、開発時は effect が2回走る。実測で track.json/laps.json/lap.json/satellite_meta/features3d.json が各2回、terrain_meta.json は4回取得。
  • 本番ビルドでは StrictMode の二重実行は起きないため、これは開発体験上の話。ただし二重マウント時に TrackBuilder が2度組まれる点は開発時の負荷源。

起動時に「読み込まれていない」もの（懸念の否定・検証済）

  • scene.glb（40MB）/ scene.mod.glb（56MB）: 取得0件。「drive on AC」有効化時にのみ遅延取得（ReplayScene.ts:239–255, 374 ensureAcAssets）。ユーザープリセットは driveOnAc:false。
  • imagegen_trials（440MB, 91タイル）/ corridor_x2 SRタイル（141枚）: 取得0件。EnhancedCorridorGround.update()（EnhancedCorridorGround.ts:206–242）が視錐台内かつ画面占有 ≥64px・距離 ≤200m のタイルのみ逐次取得。起動直後のカメラ位置では対象0。マニフェスト(小)のみ取得。
  • 他の衛星バリアント（satellite.jpg 3.5MB, bing 8MB, bing_sr 9.9MB, sr 等）: 取得0件。ユーザーモードは可用性プローブを行わず、許可された1枚（shizuoka_x2→実体 satellite_shizuoka.jpg）のみ（dataLoader.ts:150–152、satelliteVariants.ts:33–39,66）。2026-07-17の調査で指摘された「29MBファイルへのHEADプローブが5.8〜8.9sブロック」は解消済みを確認。
