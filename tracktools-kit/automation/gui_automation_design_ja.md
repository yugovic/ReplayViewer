# Track Tools GUI 工程の自動化 — レビューと確定設計

作成: 2026-07-11 / ステータス: **確定・実験完了**(結果は §6)

> **2026-07-11 実験結果の要約:** マテリアル欠落は「ヘッドレス限定バグ」では
> なかった(GUIモードでも同一出力)。真因は glTF エクスポータがカーブ realize 時に
> マテリアルスロットを落とすことで、`viewer_export.py` の `_realized_copy` 修正で
> **ヘッドレスのまま完治**。急コーナーの切れも現ビルドでは無し(数値検証済み)。
> よって B-1/B-2(GUIモード運用)は**不要になった**。§6 参照。

## 1. 背景と問い

トラック制作パイプラインは「自動(経路・標高・エクスポート)」と「対話(幅・縁石・装飾)」に分業済み
(経緯は `README_automation.md` と `../fuji/04_interactive_width_kerbs.md`)。
Track Tools はヘッドレス(`blender -b`)だと Blender 5.1 でマテリアル伝播が壊れ、
急コーナーで路面メッシュが切れるため、対話工程は GUI 前提になっている。

**問い:** この対話工程を Claude の Computer Use で自動化できるか?

## 2. 選択肢レビュー(結論つき)

### A. Computer Use で Blender GUI をマウス操作 — ❌ 不採用

技術的には可能だが、以下の理由で見送り:

1. **3Dビューポート操作が最大の弱点。** 幅トレースはカメラ依存のピクセル座標での精密ドラッグで、
   Computer Use が最も失敗しやすい操作。失敗しても気づきにくい。
2. **遅くて高コスト。** 1操作ごとにスクリーンショット→推論のループ。
   数百点のエッジ調整のような反復作業には不向き。
3. **実行環境がない。** Claude Code(この開発環境)には画面操作ツールがなく、
   Computer Use API(beta)で別途エージェントアプリを組む必要がある。それ自体が一つの開発課題。
4. **bpy で 100% 代替できる。** メニュー/パネル操作レベルなら Python API で決定論的に実行でき、
   ピクセル操作の不確実性がゼロになる(→ 案B)。

例外的に意味があるとすれば「bpy に API がない UI 専用機能を触る」場合だが、
Track Tools = GeoNodes モディファイアなので該当なし。

### B. GUI モードの Blender を bpy で操作 — ✅ 採用(2形態)

Track Tools の「GUI でしか正常動作しない」問題は、**GUI モードのプロセスに bpy を注入すれば
マウス操作なしで回避できる**可能性が高い。

- **B-1: ワンショット実行(まずこれ)**
  `blender <track>_staging.blend --python <script>.py`(**`-b` を付けない**)。
  GUI ウィンドウが開いた状態でスクリプトが走る。スクリプト末尾で
  `bpy.ops.wm.quit_blender()` すれば自動で閉じる。
  ソケットサーバ不要・追加アドオン不要で、既存の `viewer_export.py` /
  `build_track_blender.py` をそのまま GUI コンテキストで実行できる。
  制約: ディスプレイが必要(このWindows機ではOK。CI/サーバでは不可)。

- **B-2: 常駐コマンドポート(反復調整が必要になったら)**
  ソケットサーバアドオン(自作 or blender-mcp 系)を GUI Blender に常駐させ、
  Claude が bpy コードを送って対話的に操作する。
  **注意: bpy はメインスレッド以外から触るとクラッシュする。**
  受信スレッドはコードをキューに積むだけにし、`bpy.app.timers` でメインスレッド実行すること。
  バインドは localhost 限定(任意コード実行ポートなので)。
  B-1 で足りる間は作らない。

既存資産(staging blend / `tuned.json` / `EXPORT_FOR_VIEWER.py`)はそのまま使う。
B は「人間が GUI でやっていた Run ボタン押下や値変更を bpy が代行する」だけで、
ラウンドトリップ設計は変わらない。

**留保:** 急コーナーの路面切れは Track Tools がドキュメントで認めている
curve-to-mesh の不具合の可能性があり、その場合 **GUI モードでも直らない**。
実験1で切り分ける。直らない場合の回避策: 路面はネイティブバックエンド
(実績あり・連続・テクスチャ正常)に固定し、Track Tools は縁石・マーキング・装飾だけに使う。

### C. 幅決定を画像解析で行う — ✅ **実装済みだった**(前回提案の訂正)

前回「作る価値がある」と提案したが、リポジトリ確認の結果 **既に実装されている**:

- `track-creator/src/image-analysis/` — 衛星画像から左右エッジの横オフセットを
  DP 最適化で推定(`analyzeWidth.ts`、平滑性/勾配/事前分布ペナルティ)、
  信頼度算出(`confidence.ts`)、高信頼のみのブレンド適用(`proposalBlend.ts`)。テスト付き。
- エディタ UI 統合済み(`editor/analysisController.ts` + `analysisOverlay.ts`):
  画像ロード → 解析 → 信頼度色分きプレビュー(緑/黄/赤)→
  「高信頼のみ適用」/「全適用」/「破棄」。適用は 1 スナップショットで undo 可能。
- 入力の `public/data/tracks/fuji/satellite.jpg` + `satellite_meta.json` も存在済み。
  エディタの vite サーバが親リポジトリの `public/data/` を `/data/` で配信する。

つまり残タスクは「実装」ではなく **実走と精度検証**(実験2)。
ライセンス注意は従来どおり: 衛星画像はトレース参照専用。出荷テクスチャには使わない。

### D. Playwright で Web エディタを数値操作 — ✅ 採用済み(現状維持)

E2E で常用中(`snap_editor.mjs` / `snap_edges.mjs`)。`window.__editor` 経由で
座標を数値指定して操作できるため、AI がエッジ微修正を行う経路としては
Computer Use より確実。新規作業なし。

## 4. 次のステップ(優先順)

1. **実験1(B-1、~30分):** `blender fuji_staging.blend --python` で
   `EXPORT_FOR_VIEWER.py` 相当をGUIモード実行し、ヘッドレス出力と比較。
   判定基準: (a) 路面マテリアルが glTF に載るか、(b) 急コーナーの路面が連続か。
   (a)(b) とも直れば Track Tools フル出力を自動化に戻せる。(b) だけ残れば路面はネイティブ固定。

   高信頼のみ適用 → GLB ビルド → ビューワーで走行ラインと照合。
   目安: 既知の本線幅 ~13 m からの乖離と、低信頼区間(木陰・高架下)の分布を記録。
3. B-2(常駐ポート)は、実験1の結果「GUI モード必須の操作を反復する」需要が出た場合のみ着手。

## 6. 実験結果(2026-07-11 実施)

### 実験1: GUIモード vs ヘッドレス → 真因は別の場所にあった

同一のTTフルビルドをヘッドレスとGUIモード(`-P`、`-b`なし)で退避先に出力して
バイナリ内容を比較した結果、**両者は完全に同一**(grass のみ、道路系3プリミティブは
マテリアルなし)。「ヘッドレスだから壊れる」仮説は棄却。

診断スクリプトで評価済み(realize後)メッシュを直接検査すると、マテリアルスロットには
asphalt/markings/kerb の3枚が正しく載り、面ごとの material_index も正常だった。
つまり **Track Tools も GeoNodes も無罪**。真因は Blender 5.1 の glTF エクスポータが
`export_apply=True` で **CURVE オブジェクトを realize する際にマテリアルスロットを
落とす**こと。

**修正:** `viewer_export.py::export_glb` に `_realized_copy` を追加 —— 非メッシュ
オブジェクトは `bpy.data.meshes.new_from_object`(depsgraph 評価済み)で一時メッシュ化
してからエクスポートし、終了後に削除。export_glb は headless ビルドと GUI テキスト
ブロックの両方が使う単一の正なので、**1箇所の修正で両経路とも完治**。

修正後のヘッドレスTTビルド: materials = asphalt/markings/kerb/grass、画像3枚、
16.6 MB。急コーナー連続性も数値検証: 道路プリミティブは連結成分1、境界エッジ
4560 = ちょうど 2×2280駅(=切れ目ゼロ)。markings の2371成分は破線、kerb の3成分は
縁石区間数で、いずれも正常。

**追補(同日 07:17、ユーザー指摘で発覚):** 上記の「切れ目ゼロ」はトポロジーの話で、
**描画上は切れて見えた**。真因は道路頂点の56%が地形メッシュより下に沈んでいたこと
(最大63cm。ROAD の shrinkwrap サンプリングと地形三角形分割の差)。修正は
**TERRAIN_SHAPE を地形側にスタック**(target=道路カーブ。Track Tools 本来の想定手順)
+ ROAD `Z offset` +0.08 / TERRAIN_SHAPE `Z offset` -0.10 → 沈み 0.3%・10cm超 0.0%。
ROAD↔TERRAIN_SHAPE の相互参照で depsgraph が dependency cycle を警告するが出力は正常。
**教訓: 配備前チェックは①トポロジー ②沈み込み計測(sinkcheck) ③曲率上位コーナーの
ヘッドレスレンダリング目視、の3点セット。**

**ビューワー配備:** 修正版TT `scene.glb` を `public/data/tracks/fuji/` に配置
(旧ネイティブ版は `scene.native.bak.glb`)。`verify_track.js` PASS 4/4(d=0.000)。

**副産物(GUIモード自動化レシピ、必要になったら):** 起動スクリプトも
`bpy.app.timers` コールバックも制限コンテキストで走るため、glTF エクスポートは
`bpy.context.temp_override(window=..., screen=..., area=..., region=...)` で
ウィンドウを注入する必要がある。終了時の `quit_blender()` はアクセス違反を吐くことが
あるが出力には無害。レシピはスクラッチの `exp1/gui_wrapper.py` として動作確認済み。

### 実験2: 衛星画像からの幅解析 → 実走・適用・保存まで完了

エディタの解析UIを Playwright で E2E 実行(`snap_exp2_analysis.mjs`):
解像度 0.49 m/px、提案 2280点、高信頼 L 1858 / R 1998(81% / 88%)、欠損 0。
「高信頼のみ適用」で 3856 エッジ点を適用(スキップ 704)。

幅統計: 適用前 全周一律 13.00 m → 適用後 min 12.29 / 中央値 13.82 / 平均 16.43 /
max 28.75 m。最大値はピットストレート区間で、実際の富士の幅感と整合。
オーバーレイ(地理院最新写真)上でエッジが実路面に沿うことをスクリーンショットで確認。

`track.json` に保存し(事前バックアップ `track.json.bak-preanalysis`)、
GLBビルドまで実行(`out/fuji.glb`、215 KB、1520駅)。

### 結論(§3 マトリクスの更新)

- **B-1/B-2 は不要**: TTフル出力(路面+マーキング+縁石)がヘッドレスで完全に動く。
  対話工程として残るのは「低信頼区間の幅微修正」と「装飾」のみ。
- 幅決定: 画像解析(C)が実用レベルで動作確認済み。残りは低信頼 ~15% 区間の
  手動微修正(Webエディタ)。
- 未接続: track-creator 側の編集済み幅(track.json の edges)を tracktools-kit
  パイプラインの `tuned.json` widths に橋渡しする変換は未実装(Phase 1 残タスク)。
